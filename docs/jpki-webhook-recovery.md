# JPKI方式: 署名結果の通知を取りこぼしたときの拾い直し(MIR-1470)

## 症状

会員が「本登録承認待機」から動かない、または署名の画面から先へ進めない。JPKI方式の会員で、
署名の結果の通知(Webhook)が届かず、本人確認BPOサービスへ申請されていない
(`ekyc_request_log` の申請ID `applicant_id` が 0 のまま)。

## 起きる理由

本人確認デジタル認証サービスの検証結果通知(`POST /nexway/jpki/webhook`)は、Nexway が 15 分おきに
2 回までしか再送しない(仕様書 p.17)。次のような場合に、約 30 分以上 500 が続くと、通知が届かなかったことになる。

- 本人確認BPOサービスの障害、JPKI版の設定の漏れ(`Nexway.JpkiBpo*`・`JpkiBpoSigningSecret`)
- デプロイ中の停止、DB障害

再送が尽きた行は、`NONE`・申請ID 0・検証依頼IDあり のまま残る。

## 自動の拾い直し(定期ジョブ)

`JpkiSignatureRecoveryJob`(jobs-scheduler)が、上の行を定期的に探し、通知を受けたときと同じ処理を行う。

| 項目 | 内容 |
|---|---|
| 実行間隔 | 設定(`jobSchedulerConfig.cron.JpkiSignatureRecoveryJob`)で決める。1時間に1回(`7 * * * *`)を想定。**設定が無いとジョブは登録されない**(エラーにもならない)ため、各環境のParameter Storeに足すこと |
| 対象 | 検証依頼IDがあり、結果が未確定(`NONE`)で、BPOへ未申請(申請ID 0)、作成から **1時間以上**、**14日以内**の行 |
| 件数 | 1回に最大25件、新しい行から。ネクスウェイの検証結果取得APIの処理上限は1分に30件(仕様書 p.4)。残りは次の回 |
| 重複実行 | 前回の実行が終わっていなければ、次の実行をスキップする |

処理は、ネクスウェイの検証結果取得API(`GET /api/verification/{request_id}/result`)で確かめ、
**ネクスウェイの記録で判断する**(通知を受けたときと同じ。基本4情報は受け取らず、保存もログ出力もしない)。

| ネクスウェイの結果 | 行の扱い | 会員へのメール |
|---|---|---|
| 署名成功(`succeeded`) | 本人確認BPOサービスへ申請し、申請IDを記録する(結果は、BPOの結果通知で確定する) | なし |
| 署名失敗・エラー・中断(`failed`/`error`/`canceled`) | `FAIL` にし、エラーコードを `error_message` へ記録する | あり |
| ネクスウェイが記録を引けない(404 かつ `error_code` が `4040002`。保管期間が過ぎた等) | `FAIL` にする | あり(具体的な理由は添えない) |
| `4040002` 以外の404(ベースURLの設定誤りなど)・その他のエラー応答(403 `4030001` のIP制限、503 など) | 変えない。次の回で確認し直す(警告のログ) | なし |
| まだ確定していない(処理中・未検証) | 変えない。次の回で確認し直す | なし |

- 会員の最新の行でなければ(その後に新しい署名用URLを発行している)、メールは送らない。
- 本人確認が済んでいる会員(`is_ekyc`)、本登録が確定した会員(承認完了・無効)へも送らない。
- メールが送れなくても、行は `FAIL` のまま(行は処理済みになり、メールだけを再送する仕組みは無い)。
  送れなかったことは、エラーのログ(`failed to send the retry verification mail`)に残る。
- 全件の処理が失敗した回は、ジョブがエラーになる(設定の不備・ネクスウェイの障害など、全体の問題に気付くため)。
  一部だけ失敗した回は、失敗した行を変えずに終わり、次の回でもう一度確認する(警告のログ)。

### 署名の失敗の理由(エラーコード)

署名の検証処理でのエラー(利用者が署名を拒否した・署名用電子証明書の期限切れ・ロックなど)は、
検証結果通知Webhookにも本人確認BPOサービスのAPIにも含まれず、検証結果取得APIのレスポンスの `errors` にだけ入る
(エラーコードは仕様書 p.14)。`error_message` へ「`C04: 署名用電子証明書が有効期限切れです。…`」の形で記録する。

- C01〜C08: 仕様書のエラー詳細(利用者向けの文面)を、そのままメールの理由に使う
- C09: 何と照合するかをネクスウェイに確認中(2026-10-23)のため、確定するまでメールでは
  「署名が完了しませんでした」とだけ伝える(`error_message` には仕様書の詳細を残す)。
  確定したら `service/nexway_jpki_errors.go` の `jpkiUnconfirmedMemberReasons` から外す
- E01・E05(サービス側の事情): 記録には残すが、メールでは「署名が完了しませんでした」とだけ伝える
- `errors` の形が仕様書で食い違っている(項目表とサンプルで型が違う)ため、どんな形でも、エラーコードだけを取り出す。
  形が想定と違っても、結果の読み取りは失敗させない

### 会員へのメール(本人確認のやり直し)

テンプレート名は `JPKI_RETRY_VERIFY`。**miralita-mail-service(SendGrid)にテンプレートを追加しないと送れない**
(mail-service の別のPRで足す。JPKI方式を有効にする前に、文面の確認と追加が要る)。
変数は再本登録メール(`RETRY_SIGN_UP`)と同じ `Receiver`・`ServiceUrl`・`Reasons`。
再本登録メールとは別のテンプレートで、会員の状態は変えない(マイページの本人確認の案内から、
もう一度進めてもらう)。

## 自動で拾えないとき・確認するとき(手動)

ジョブの設定が無い、またはジョブが動いていない場合は、次の手順で手動で拾い直せる。

### 対象の行を探す

```sql
SELECT id, user_id, ekyc_id, request_id, status, created
FROM ekyc_request_log
WHERE request_id IS NOT NULL      -- JPKI方式の行
  AND applicant_id = 0            -- BPOへ申請されていない
  AND status <> 'FAIL'            -- 失敗と記録済みの行は対象外
  AND created < NOW() - INTERVAL 1 HOUR   -- 通知の再送(15分×2)が尽きたあと。NOW()はDBのタイムゾーン
ORDER BY created;
```

署名の途中の会員(まだ署名していない)も、時間が経てば同じ条件に入る。その場合は、下の手順で
Nexway に確認すると、`FAIL`(中断・期限切れ)になる。

### 拾い直す(通知を手動で送る)

行ごとに、jobs-scheduler の `POST /nexway/jpki/webhook` へ、同じ形の通知を送る(内部のネットワークから)。

```json
{"reference_id": "<ekyc_id>", "request_id": "<request_id>", "result": "succeeded", "completed_at": "2026-10-15T10:00:00+09:00"}
```

`result` は何を書いてもよい。受信口は通知の内容を信用せず、Nexway の検証結果取得API
で確認し、**Nexway の記録で判断する**。結果は上の表と同じ(失敗の場合は、会員へメールも送る)。
署名がまだ完了していなければ 500(あとでもう一度)。

何度送っても、二重には申請されない(申請ID済み・`FAIL`済みの行は何もしない。同じ会員により新しい行が
あれば、その行は申請せず閉じる)。メールも、行を `FAIL` にできた1回だけ送られる。

## 確認

- 申請された行は `applicant_id` が入る。BPOの結果通知(`/nexway/bpo/webhook`、MIR-1468)が届くと、結果が反映される
- ログ(ジョブ): `nexway jpki signature recovery: finished`(`found`・`pending`・`errored` の件数)
- ログ(行ごと): `nexway jpki signature result: bpo applicant registered`(`updated=1`)

## 補足: 「受付済み」で申請IDが入らない行

申請の直後に通信が切れた、または申請IDの保存に失敗して再送された行は、BPOが「受付済み」(4000010・4000011)
を返し、申請IDは記録されない(受付済みの応答に申請IDは含まれない)。この行の申請IDは、BPOの結果通知で記録される。
このため、上の条件に入り続けるが、確認しても「受付済み」のまま変わらない。BPOの結果通知を待つか、
BPOの管理画面で `reference_id` を検索して状態を確認する。ジョブは、新しい行から処理する(古い行が
毎回の件数の枠を使い切って、新しい行が処理されなくなるのを防ぐ)。

ただし、この行が新しい側に25件以上たまると、逆に、それより古い取りこぼしが期限(14日)まで処理されない
ことがある。起きにくい(申請の直後の通信の切断などが重なったときだけ)ため、今は対処していない。
起きた場合は、上の手動の手順で古い行を拾い直す(行ごとに「最後に確かめた時刻」を持たせて古い順に回す形は、
列の追加が要るため、別の対応として検討する)。

## JPKI方式を有効にする手順(staging を含む)

設定は、**デジタル認証サービス(`Nexway.JpkiAuth*`)とBPO JPKI版(`Nexway.JpkiBpo*` の3項目)をそろえてから**、
画面の入口(`JPKI_EKYC_ENABLED`)を有効にする。デジタル認証サービスだけを入れて BPO を入れ忘れると、
署名が成功するたびにBPOへの申請が通信の前に止まり(500)、会員が承認待機へ進めない(行は未確定のまま残り、
ジョブが毎時確かめ直す)。JPKI方式の設定が1つでも入っていて BPO の項目が足りなければ、jobs-scheduler は起動時に
Errorログ(`Nexway JPKI版(本人確認BPOサービス)の設定が足りない`)を出す。

1. Parameter Store に `Nexway.JpkiAuthBaseUrl`・`JpkiAuthToken`・`JpkiBpoBaseUrl`・`JpkiBpoToken`・`JpkiBpoSigningSecret` をそろえる
2. cron の `JpkiSignatureRecoveryJob` を足す
3. mail-service にメールテンプレート `JPKI_RETRY_VERIFY` があることを確かめる
4. ALB で `POST /nexway/jpki/webhook` を jobs-scheduler へ通し、送信元をネクスウェイのIPに限る
5. 起動時のErrorログが出ていないことを確かめてから、画面の入口を有効にする
